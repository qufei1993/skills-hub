# 资源归属、异步执行和失败

每个资源和状态变化都应有一个明确负责方。追踪分配、对外提供、使用、取消和释放，包括重入和等待。借用的数据不得擅自修改，也不能在其负责方生命周期结束后继续持有。共享缓存需要明确作用范围、失效规则和权威数据源；派生视图应在文档规定的成功时点达到一致。

回调可能重入前，先登记资源归属。每次等待后，在对外提供结果前确认负责方和操作仍然有效。清理时先阻止新工作，再取消或等待正在运行的使用者，解除回调，最后释放它们的依赖。只有被释放资源的使用者都不可能继续运行，释放过程才算真正结束。一项清理失败不能悄悄跳过其他独立清理，应报告相关失败。

在恰当的处理位置区分预期业务失败、调用错误、环境失败和意外缺陷。使用项目稳定的类型化错误标识，不从自然语言消息猜测类型，也不把所有异常重标为同一种业务错误。保留原因和有用上下文，不携带秘密。

抛出异常不等于已回滚。区分尚未开始、未变化、部分提交、已提交和结果未知。状态负责方必须确认恢复、继续或重试的前提。结果未知时，需要核对真实状态或依靠幂等约定；无条件重试可能重复已经提交的操作。前提无法建立时，停止依赖该状态的后续工作。

用户反馈应由失败操作的负责方提供，准确说明剩余状态和可执行的下一步。底层捕获与顶层通知不应同时争夺处理责任，或悄悄给出矛盾信息。
