# 日常编码与设计选择

使用项目的语言和现有设计，把下面的检查应用到正在修改的代码。重点是行为和职责归属，不是增加一套新框架。

## 输入、默认值和配置

- 在理解参数含义的负责模块集中解析可选输入和默认值，再将解析结果传给执行逻辑。显式零值、false 或空值不得意外被默认值替代。说明哪些值表示“未指定”。
- 只有运维确实需要按部署环境调整的选项，才做成配置。协议值和安全约束保持固定。加载时验证配置；存在外部引用时，在最早能解析它们的位置验证。配置无效应报告错误，不悄悄关闭用户请求的行为。
- 对来自 JSON、文件、持久化存储、队列、进程、网络和其他不可信调用方的数据做校验。找到建立内部类型保证的解析位置。内部接口已经强制排除的值，不应仅为处理它们而重复检查或添加回退分支。动态语言或运行时可扩展接口，可能需要静态类型系统在其他语言中提供的检查；依据真实调用方判断，不机械套用语言层面的口号。

## 类型与错误

- 跨组件传递、容易混淆的标识符，按语言惯例使用不同类型。不要为了一个局部修改，把整个项目改造成专用 ID 框架。
- 取值集合封闭时，让漏处理显式失败，语言支持时使用穷尽检查。取值可扩展时，定义未知类型的处理方式，避免无意封闭的分支拒绝未来实现。
- 只捕获当前确实能分类或恢复其失败的操作。保留调用方区分拒绝、部分完成和结果未知所需的信息。清理和尽力报告都应有明确负责方；吞掉所有错误可能把损坏状态伪装成成功。

## 依赖与扩展点

- 追踪受影响模块的公开导入、导出和真实调用方，保留项目的依赖方向。底层组件不应仅为获得类型或配置值就导入应用层或 UI；共享定义应放到实际负责维护它的位置。涉及对象身份、注册表或共享状态时，检查循环依赖和重复实例。
- 明确扩展点的定义、实现和使用方。只有这些角色独立演进，或已有具体的第二个实现方或使用方时，才拆分。设想中的未来插件，本身不足以证明需要注册中心、通用工厂或独立包。公开且受支持的扩展点，即使本地只找到一个实现，也应保留。
- 注册就是获取资源：返回或保存注销方式，指定生命周期负责方，必要时验证释放和重新注册。不要通过修改其他组件的私有注册表来补救职责归属。
- 现有且持续维护的依赖若能实质减少自有代码和测试，应在核实适配性与项目依赖政策后优先使用。不要为简单操作新增依赖，也不要仅为避免声明依赖就复制整个库。

## 按需要使用

选择满足请求行为和受支持调用方的最小完整改动。未来维护者需要理解的长期取舍，应写入项目决策记录；局部机械选择可留在聚焦注释或改动摘要里。按失败机制选择测试，不按改动行数凑测试。
