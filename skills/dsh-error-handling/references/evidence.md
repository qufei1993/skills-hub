# 证据与验证

证据应对应到实际检查的版本、工作区、命令、配置和运行环境。检查用户实际使用的包、CLI、服务或调用方。针对手工替身的单元测试，不能证明交付入口能够正确加载、组装依赖或运行。预先启动的服务、预期端口上的旧构建，都不能证明当前改动正确。

阅读项目必需检查并保留其范围。针对性检查能提供反馈，但不能替代规定的完整检查。分清通过、失败、跳过、未运行和环境阻塞。退出码为零，但没选中测试或只跑了空壳命令，不能证明目标行为。查看输出、测试数量和变化的快照。重复已通过的测试，应有明确要排查的问题。

从公开行为约定或独立判据推导期望结果。不能只用 Agent 的成功报告、刚覆盖的快照、复制实现的逻辑或私有状态来判定正确。新增防护或检查时，在隔离环境故意违反规则，确认真实顶层入口会拒绝；恢复样例后，再确认合法情况通过。不要为此破坏用户工作。

并发、时序和清理问题应暴露并等待相关状态变化。固定休眠、串行执行、重试和过宽超时可能掩盖竞争。验证真实的进程与任务组织方式；如实解释环境限制，不编造等价证据。日志可能包含任务数据，公开证据应限定范围，去除凭据和私有机器路径。

只有对应工具调用确实执行或被拒绝，才能说某条命令已尝试。不得编造执行、权限错误或沙箱限制。只读审查仍可使用获授权的临时探针；无法使用时，区分真实工具拒绝与根本未执行的检查，并引用实际诊断。

执行检查时，在工作笔记保留命令、工作目录、相关配置和观察结果。最终回复前，对照真实工具结果核实执行声明。分别标注源码检查、外部提供的历史日志和建议检查。对用户的报告保持简洁；工作笔记不要求新增受版本管理的文件，也不要求在答复里堆放大检查表。

完成报告应说明修改或发现、实际检查及结果、观察到的用户行为和剩余不确定性。不能将部分验证矩阵标为全部完成。
