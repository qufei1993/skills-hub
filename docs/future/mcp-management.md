# MCP 管理：未来功能讨论

状态：仅供讨论，当前不实现、未排期、未指定发行版本。2026-10-30 确认保留讨论材料；不属于本次技能预设与内容更新的交付范围，也不要求下一版实现。

## 希望解决的问题

用户可能在多个 AI 工具及项目中重复维护 MCP 配置，难以判断哪些连接在哪里使用、配置是否发生变化，以及失败由运行环境、凭据还是客户端授权引起。早期原型探索了统一查看和配置这些连接的方式，尚未证明需要建设完整的 MCP 管理工作区。

当前选择是保留需求和模拟原型，暂不开发。这样可以在出现明确使用场景时继续评估，同时避免扩大当前版本范围。暂时也不向技能预设加入 MCP 成员。

## 可讨论的方向

| 方向 | 需要回答的问题 |
| --- | --- |
| 查看与导入已有配置 | 是否只需查看各工具配置？如何明确扫描范围，避免把发现条目误当作允许修改？ |
| 保存连接与分配目标 | 是否需要集中保存定义？定义与实际工具、全局和项目配置如何区分？ |
| 配置变更与冲突 | 如何保留注释和无关条目，识别外部修改，并展示真正会改动的位置？ |
| 连接检查 | 是否需要主动检查？什么情况下会启动命令、读取凭据或请求授权，如何明确告知用户？ |
| 记录与撤销 | 是否值得维护写入历史？如何保护后续修改、复用和其他管理工具的配置？ |

以上是候选问题，不是待实施清单。完整管理、有限的查看／导入能力，以及继续交给原客户端管理，都保留为评估选项；目前没有选定实施方案。

## 进入实施前需要重新确认

先确认真实使用场景和最小范围，再核实客户端适配能力。原型曾使用 Claude Code、Cursor、Codex 作示例，不构成支持承诺；配置格式、路径、凭据传递、授权与重载行为需按届时版本验证。Skills 的工具支持数量不能直接用于 MCP。

若未来纳入开发，必须单独明确配置写入权限、敏感信息存储、并发修改及撤销边界，并设计真实客户端和跨平台验证。常驻代理、进程托管、自动安装运行环境、聊天、供应商切换和在线分享均不因本讨论而获得实施授权。

## 材料与证据范围

[讨论原型](../../work/prototypes/next/README.md)保留了 2026-10-24 的设计说明、评审记录和模拟交互。`next` 只是原有目录名，不代表版本承诺；原型源码、生成页面和检查脚本随仓库保存，便于后续复现；它们不接入应用构建、运行入口或发布包。原型中的服务、路径、授权、连接检查和文件操作均为模拟，既有评审只证明当时的原型交互，不证明真实 MCP 能力可用。

原型不要求持续同步当前应用 UI，重新讨论时再决定是否值得更新。固定设计基线保持不变，当前产品能力仍以[实施说明](../releases/v1.1.0/implementation.zh.md)为准。只有另行确认需求、范围和验证方式后，才建立开发计划。
