# 设备同步：文本三方自动合并

## 行为

仍使用上次同步基准、本机导出快照和远程最新提交进行比较。不同文件及单边改动沿用原有规则；同一文本文件被双方修改时，使用现有 git2 0.19 / libgit2 尝试自动合并。

检查变化与实际同步共用同一判断逻辑。无冲突时将合并内容写入同步工作区，重新计算文件哈希与 Skill 哈希，并进行现有私钥文件检查。推送成功后才更新托管库。

## 安全边界

- 三个输入均为 UTF-8、没有 NUL、各不超过 1 MiB；其他输入保留冲突，不进行强制文本处理。
- 使用自动清理的临时裸仓库、固定内置文本驱动，不执行外部 Git 命令或仓库脚本；不选择 ours、theirs、union。
- 从确定的提交读取基准和远程文件，核对三份输入与清单的哈希。缺失、篡改、越界路径和符号链接按错误处理。
- Git 历史快照发生 LF/CRLF 归一化时，仅接受与清单 SHA256 完全一致的换行还原；本机快照不放宽验证。合并保留本机一致的换行格式，混合换行不自动合并。
- 没有基准、双方新增同路径、一方删除另一方修改、元数据歧义仍需用户处理。
- 任一未解决冲突阻止整轮发布与本机内容应用；不会安装冲突标记文件。
- 修复远程拒绝分支更新时可能被误认为推送成功的问题，保留本机内容和旧同步基准。
- 私钥检测扫描完整文件而非前 4 KB，覆盖 PKCS#8、OpenSSH、RSA、EC、DSA 和加密私钥标记；错误不回显内容。此检查不是任意敏感信息的通用检测器。
- 合并是文本级，不保证自然语言语义或任意嵌入代码/YAML 的正确性。
- 不改变凭据读取、数据库格式、公开上传确认及现有冲突处理界面。

## 验证范围

真实本地 Git 仓库模拟两台设备：同文件不同段落合并、单边新增/删除及标签保留、只读检查、清单哈希一致、后续同步幂等、混合可合并与不可合并文件、远程拒绝推送。

单元测试覆盖重叠修改/插入、Unicode、CRLF、末尾无换行、空输入、相同结果、二进制、非 UTF-8、大小限制、缺失基准、删除冲突、元数据冲突、快照完整性与生成内容安全检查。

累计新增 17 项 Rust 测试（包含多组参数场景），后端全量 317 项测试及 Clippy 通过。已验证“不同段落仍报冲突”“远程拒绝被当成成功”和真实 Git 换行归一化导致哈希不匹配三个用例先失败、修改后通过。

再次自审补充了双向插入/删除、双方相同修改叠加独立修改、空文件、空白字符保留和精确大小上限测试；真实仓库测试确认过期推送不能覆盖新提交，推送失败解除后能重新合并并让两台设备收敛。另有两项回归断言先复现文件后部私钥标记漏检，修复后通过。

标准 `npm run check` 的默认配置加载受主检出目录 package.json 既有合并冲突阻断。未修改主目录，改用工具支持的 `--configLoader runner` 完成同一前端测试套件（14 文件、121 项通过）及 Vite 生产构建；TypeScript 编译、ESLint、Rust 格式检查、Clippy 和 317 项 Rust 测试分别通过。构建仍有混合静态/动态导入与大分块警告。本次没有修改前端，当前 worktree 的开发后端已热重编译并启动。
