# AI management diagnostics and recovery

Production setup downloads the matching CLI through a public GitHub asset URL. A draft release is not accessible through that URL, even when its owner can download assets from the release page. A 404 may also mean that the release or the platform asset is missing. The UI explains these possibilities and requires publication with the matching CLI asset, rather than suggesting repeated retries. Local CLI validation and the failed installation are separate results; installation details now show their relationship.

Readiness ignores damaged historical targets belonging to disabled or undetected tools, while preserving their per-tool diagnostics and files. PATH conflicts no longer hide the repair action when terminal setup is incomplete. A library refresh failure after successful enablement preserves the successful status and gives a separate refresh instruction. The official Skill no longer promises startup updates.

Regression tests cover unavailable downloads in English, Chinese and Korean, distinct download/integrity failures, terminal repair with a PATH conflict, library refresh failure, and missing/disabled historical tools using temporary directories. Draft-only testing does not establish that anonymous production CLI downloads work after publication. A verified existing CLI can work offline; fresh production setup against a draft cannot.

Enable now directly repairs the managed official central copy, including a modified copy or a missing recorded checksum. This is restricted to the owned regular official directory; other sources, unsafe paths and modified tool targets remain protected. Transaction failures restore the original files and record. Same-version changes to the bundled Skill expose an explicit update action. Terminal setup supports Bash and Zsh on macOS/Linux and the user PATH on Windows; failure after Skill deployment can leave a partially completed setup, which requires fixing the terminal configuration and retrying.
