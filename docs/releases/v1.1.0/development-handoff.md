## 开工顺序

1. **核对当前工作区及真实页面。** 当前分支为 `feat/v1.1.0`，工作区存在其他未提交修改。记录现状，区分已有工作，不覆盖或还原无关改动。以当前 `App.tsx`、实际组件和生效样式为准，不直接将演示 HTML 替换进生产。
2. **补齐技术契约及任务清单。** 在本目录新增实施任务文档，明确下面三类契约，核对现有库与服务后作实现决策。常规实现选择自行推进；若必须改变已确定的产品行为，应先明确变更及影响。
3. **先实现目标模型与共同执行服务。** 在真实临时目录和持久库中验证范围、预览、执行、部分失败、重试及撤销，再接入项目和预设页面。
4. **接入更新恢复和就地修复。** 各写入口复用一致的检查与保护；最后完成现有功能回归、跨平台路径验证、页面及键盘验收。

## 三类技术契约

### 目标身份与迁移

区分中央 Skill、逻辑工具目标、物理目录三层身份。明确旧数据如何迁移、目标如何唯一标识、删除重建如何区分代次。添加项目目标不能迁走全局目标。工具共享目录、大小写与路径规范化按实际适配器核实，不能把原型中的工具示例硬编码成通用规则。

### 写入、记录与恢复

确定预览依据、再次确认条件、重复提交处理、逐项记录落库时点、中断后续作与操作锁。撤销依据本次实际新增和后续使用情况，保护个人修改、其他操作的引用及已重建目标。更新恢复应包含文件内容、必要版本元数据和来源基线；应用重启后记录及恢复能力仍应有效。

### 接口与现有入口

明确 UI 与共同服务的数据结构、错误分类和逐项结果。检查既有手动、批量、自动、CLI、设备同步写入口；同一行为遵守同一保护规则。演示数据中的成功、失败、共享目录示例必须替换为真实检查结果。

## 生产验收重点

- 预设创建、编辑、复制、删除仅修改定义，不产生部署变化；逐成员工具分配往返保存准确。
- 全局与项目互不迁移；项目移除不删除中央内容、其他项目或仍被引用的物理目录。
- 多项目部分失败保留已成功项；重试仅处理未完成项；重复请求不产生重复写入。
- 预览后内容、来源或目标变化时重新核对；中断和重启后记录不丢失，能解释当前结果并继续处理。
- 历史快照不因模板编辑、改名或删除而改变；可找到较早记录；撤销保护后续使用、修改和目标重建。
- 两个 Skills 更新后各自可恢复；恢复保留后加部署，拦截后续内容修改，同时恢复必要来源基线。
- 保留原列表、批量操作、更新计划和详情能力；空态、长列表、长路径、键盘、返回来源及窄窗口仍可用。

已有原型检查验证的是模拟行为。可以重跑 `work/prototypes/review/` 的检查，但不能用其通过代替真实文件操作和持久化测试。

## 与下一轮设计并行

- 研发会话维护生产代码、实施任务及验证记录；设计会话只维护 `work/prototypes/next/`。
- 新设计不覆盖本目录固定原型，不顺手扩大 1.1.0 范围。
- 同一仓库目录内并行工作时保持现有分支，按文件范围协作，不互相切分支或进行仓库范围的重置。如需不同分支并行，使用独立 Git worktree。
- 研发中确需改变界面或行为，记录变更及原因，并将实际落地结果同步到下一轮设计。不要静默重写已固定稿；需要新基线时增加明确修订。
- 提交前按文件核对本次工作范围，避免将未完成的下一轮草稿或其他会话修改一起纳入。
- 仓库材料只记录自身需求、设计和验收；外部产品调研资料保留在仓库外。
